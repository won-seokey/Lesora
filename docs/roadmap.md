# 실행 로드맵

기준 계획서 Phase 0~4 유지. `[x]`는 이번 코드/문서 작성 완료, `[ ]`는 후속 작업이다. 코드가 작성되어도 실제 공급자 검증이 끝나기 전 Phase 완료로 표시하지 않는다.

## 우선 후속 작업 — 2026-11-04 기록

### 다음 작업일(내일, 2026-11-05 예정): AI 리뷰 설정

현재 사용자 확인 기준으로 API 키/모델 관련 Repository Secrets·Variables 설정은 미완료다. 워크플로 dry-run 성공과 실제 모델 리뷰 성공을 구분한다.

- [ ] AI-01 사용자: Repository Secrets에 `GEMINI_API_KEY`, `DEEPSEEK_API_KEY`, `OPENAI_API_KEY` 등록. 우선 시험할 공급자 하나만 먼저 등록해도 된다.
- [ ] AI-02 사용자: Repository Variables에 `PR_AGENT_MODEL_GEMINI`, `PR_AGENT_MODEL_DEEPSEEK`, `PR_AGENT_MODEL_OPENAI` 설정. 모델 접근 권한·API 등급·최신 가격과 고정 PR-Agent 이미지의 호환성을 실행 전에 확인한다. 이전 대화의 모델 추천을 실행 검증 완료로 취급하지 않는다.
- [ ] AI-03 기본 공급자 `PR_AGENT_PROVIDER`를 결정하고 `PR_AGENT_AUTO_REVIEW=false` 유지. 키/모델명은 [설정 가이드](ai-review.md)를 따른다.
- [ ] AI-04 에이전트: PR #1의 코드 리뷰·필수 CI·사용자 병합 승인 절차를 거쳐 워크플로가 main에 포함되도록 준비한다. main 병합은 별도 승인 후 수행한다.
- [ ] AI-05 main 반영 후 작은 내부 PR에서 수동 dry-run → 실제 모델 리뷰 → 한국어 댓글·응답 잘림·토큰 사용량·실패 처리를 확인한다. 실제 호출은 사용량 승인을 전제로 하며, 초기 PR #1은 파일 수 제한 초과로 실제 리뷰를 건너뛴다.
- [ ] AI-06 결과와 비용을 확인한 뒤 자동 리뷰 활성화 여부 결정. 활성화 전까지 자동 API 호출을 시작하지 않는다.

완료 조건: 최소 한 공급자의 작은 PR 실제 리뷰가 검증되고, 사용량·검토 누락 범위가 확인되며 자동 실행 정책을 결정한 상태. 날짜는 작업 예정일이며 예약 실행/알림을 설정한 것은 아니다.

### 이후: 정적·동적 검증 및 CI/CD 도입 계획 수립

목표: 실제 팀 개발 흐름에 맞게 PR 작성/수정, main 병합 후, 배포 전후에 수행할 검증과 실패 시 처리 기준을 먼저 설계한다. 아래는 **계획 수립 작업 목록**이며 도구 선정이나 신규 파이프라인 구현 완료가 아니다.

- [ ] QA-01 기존 검사 목록과 공백 조사: 현재 `Checks / check`의 테스트·HTTP 통합·타입·린트·빌드·Compose 검사와 AI 리뷰 dry-run을 실행 내용 기준으로 분류한다. HTTP 테스트는 동적 검사이며 AI 의견은 정적 분석 도구의 보증이나 테스트 통과를 대체하지 않는다.
- [ ] QA-02 이벤트별 검증표 작성: PR 생성·새 push·Draft→Ready, main 반영(`push`), 수동 실행·정기 점검, staging/production 배포 전후를 구분한다. PR 빠른 피드백과 main 통합 회귀의 범위·중복 실행·취소·시간 예산을 정한다.
- [ ] QA-03 정적 검증 계획: 타입/린트, SAST, 의존성 취약점·라이선스, secret 탐지, Docker/워크플로 설정 검사 후보를 비교한다. 무료 사용 범위·유지보수·오탐·권한을 평가하고 필수/권고 여부와 차단 심각도·예외 만료 정책을 정한다.
- [ ] QA-04 동적 검증 계획: 단위·API/DB 통합·브라우저 E2E·접근 권한/재접속 회귀·실행 중 앱에 대한 DAST·배포 smoke·성능/부하 시험의 범위와 실행 환경을 정한다. DB migration/복원 시험 및 테스트 데이터·격리·실패 증거 수집도 포함한다.
- [ ] QA-05 RTC/녹화 분리: 공급자 없이 가능한 mock/계약 검증과 실제 SDK·브라우저·불량망·녹화 E2E를 구분한다. 실제 외부 사용량이 발생하는 시험의 실행 시점·예산·승인·credential을 정한다.
- [ ] QA-06 병합/배포 게이트 설계: 안정화된 검사만 main 필수 검사로 지정하고, 검사 실패·flaky 테스트·API 장애·부분 skip의 처리와 리뷰 책임을 정한다. 사용자 main 병합 승인 정책을 유지한다.
- [ ] QA-07 CD 설계: main 검증 후 동일 이미지의 staging 배포·동적 검사·production 승인/승격·health 확인·rollback 흐름을 정의한다. main에 push되었다는 이유로 바로 production 배포하지 않는다. 실제 배포 환경과 목표 복구 시간을 먼저 정한다.
- [ ] QA-08 실행 보안/비용: 외부 fork의 비밀키 접근 차단, 최소 token 권한, Action 버전 고정, artifact 보관/민감정보 제거, 러너·저장소·모델 API 비용 한도를 설계한다.
- [ ] QA-09 산출물 작성: 별도 검증/CI-CD 설계 문서에 이벤트×검사 매트릭스, 도구 비교·선택 근거, 통과/차단 기준, 단계별 구현 티켓과 완료 조건을 작성하고 리뷰한 뒤 순차 도입한다.

완료 조건: 현재/목표 검증 범위가 구분되고, PR→main→staging→production의 게이트·실패 대응·비용·도입 순서를 검토할 수 있는 계획이 마련됨. 구현 전 작업 규모에 맞게 필수 검사부터 점진 도입한다. 현재 CI/CD를 운영 준비 완료 상태로 표시하지 않는다.

## Phase 1 — 공통 실시간 강의실 MVP

의존성: Phase 0 선정/회귀 시험 자료, 수업 규모/권한 정책. 세부 작업:

1. DB migration과 auth/users: 비밀번호 해시, 세션 쿠키, CSRF, 계정 중지, 역할 테스트.
2. courses/enrollments/lessons: 소유권 검사, 일정 타임존, 예약/시작/종료 상태 전이, 중복 명령 처리.
3. 실제 사용자/참여 ID 기반 토큰, 강사/학생 레이아웃, 장치 선택 및 입장 전 점검.
4. 채팅 저장 후 전달, 메시지 UUID 중복 제거, 입퇴장 이벤트·단절/재입장 상태 복원. 이벤트 식별자/발생·수신 시각을 남겨 향후 사용량 대사의 근거를 확보한다(현재 결제 구현 제외).
5. 강사/발화자 영상 구독, 음성 우선 자동 정책·복구 지연, 오류/재시도 UI.
6. Phase 0 녹화 시작 연동을 수업 서비스에 연결하고 상태 표시(운영 완성은 Phase 2).

검증: 수업별 IDOR 음성/영상/채팅·재접속 통합 테스트, 목표 정상망 입장 p95 ≤15초·채팅 p95 ≤1초. 완료: 강사와 여러 학생이 외부 PC에서 수업·복구를 수행하고 저장된 출석/채팅을 조회한다. 녹화 없는 상태로 출시 승인하지 않는다.

## 출시 이후 외부 강사 SaaS 검토 게이트

기존 Phase 0~4 순서와 결제의 후속 범위를 유지한다. 유료 이용권 도입 전 판매 단위/포함 인원·동시 방·녹화/보관량, 전체 원가와 크레딧 만료 후 손익, 계량 대사·원장·기관 격리·환불 정책을 정한다. 잔액 부족 시 사전 경고, 신규 수업 제한, 유예, 자료 저장·RTC/녹화 종료 및 실패 복구를 시험한다. 시간당 2,000~2,500원은 검증 전 가격 가설이며 구현·판매 승인이 아니다. 정책과 실제 청구가 일치하는 시험을 통과한 후 별도 출시 결정한다.
